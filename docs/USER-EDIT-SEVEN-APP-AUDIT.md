## Source behavior and field classes

**5pay.** `src/main.js`, `src/views.js`, `src/data.js`, `src/integration.js`: user enters `state.mode=edit`; page-level panel is appended to flow, not all controls inline. Pages include START, P1–P7, scenario-derived pages and `LOCAL_*`; official page ids are data-driven. `ava-saving-user-overrides-v1` localStorage stores overrides; save helper catches write errors, and ordering/add/delete currently write immediately. Return uses recognized parent/referrer context via `avaReturnHref`; a missing context returns null and actual fallback needs verification. Admin is separate entry; URL alone is no authorization. Existing field patterns: `customPages[LOCAL_*].title/subtitle/content` **ALLOW** only for user-authored non-product copy; `customPages[LOCAL_*].media` **ALLOW** as cloud references subject to Mother media rules; `pages[page_id].title/subtitle/hidden/order` and `cards[id].headline/subtext` **REVIEW REQUIRED** per page/card because official meaning or disclosure may be altered; product rates, multipliers, totals, official rows, illustrations and credentials **PROTECTED**. Need staged drafts, per-field allowlist, rollback, return fallback and readback; no claim of executed browser behavior.

**Medical.** `app.js`: user entry invokes edit on real Ready/Not Ready flow; `data-field=title/subtitle` text draft is per page; `p7Comparison` is separately saved on changes. Mapped IDs R01–R10, N01–N07 and FINAL_SUMMARY, with actual Ready order and availability controlled by source data. `OVERRIDE_KEY` localStorage holds text and P7 model; current P7 writes bypass global draft. Admin gate uses `MedicalAdminAuth`; user return currently goes to AVA root, admin to `avaSurface=admin`, so user surface must be corrected/tested without weakening auth. `title`/`subtitle` per page **REVIEW REQUIRED** until meaning checked. Premiums, deductibles, eligibility, sources and calculations **PROTECTED**.

P7 classification is by owner, item identity and meaning, not `main_value` or `sub_value` alone. Current source identifies custom items through `userCreated` / `customItems` and official-item modifications through `overrides` keyed by item; this is audit evidence, not by itself proof that all saved text is safe. Preserve legitimate P7 personalization:

| Existing field / operation | Classification | Boundary |
| --- | --- | --- |
| User-created item `item_name`, `main_value`, `sub_value`, creation/edit/delete, User-owned notes and presentation descriptions | **ALLOW** | For genuinely User-owned explanations and presentation that do not misrepresent or replace Official coverage; even a User-created value purporting to state Official limits or conditions requires review, not automatic trust. |
| `sort_order`, `enabled` for User-created items | **ALLOW** | Subject to preserving any mandatory product disclosure elsewhere on the page. |
| Official item `item_name`, `values[plan][condition].main_value/sub_value` representing Official benefit, limit, conditions or qualification | **PROTECTED** | Never overwrite authoritative Official content with a User override. |
| Official item `enabled` / `sort_order` | **REVIEW REQUIRED** | Conditionally permitted only after confirming required disclosures remain visible and meaning is preserved. |
| Existing Official-item overrides, including `main_value` / `sub_value`, whose origin or meaning is ambiguous or mixed | **REVIEW REQUIRED** | Classify individually; preserve original, split Official fact and User explanation where safe; no silent deletion, conversion to authoritative facts or loss of local data. |
| User explanatory notes and additional presentation text | **ALLOW** | Separate and label as User-owned; do not contradict or conceal Official facts. |

The model's immediate P7 writes must be migrated to staged Preview/Save/Cancel/readback. Inventory old overrides and custom items; retain an exact backup in the existing User ownership boundary, define reversible field-level mapping and readback, and test reload/rollback. If classification is unknown or no safe migration exists, retain the original for recovery and block only that dependent migration; do not erase it or publish it. Whether a custom item asserts product facts cannot be determined solely by `userCreated`.
