# Unified User Edit v1.0 — implementation specification

Status: product-owner approved UI direction; detailed implementation contract proposed for PR #79 final review. Governing sources: [Mother Rules](MOTHER-RULES.md), [AVA Design System](../design-system/DESIGN-SYSTEM.md), its tokens and components. Their current merged versions govern where this document is silent. Product logic takes priority over visual similarity. These specifications apply to presentation editing only; App journeys, storage and releases remain independent.

## Anatomy and states

| State | Placement and behavior | Transition / evidence |
| --- | --- | --- |
| Frontend | Existing customer flow; no edit controls or User toolbar. Header left has App identity with independent version beside it, right has visible outlined directional icon plus 返回 AVA. Preserve page controls and journey navigation. | `frontend` and bare URL open customer flow; no Admin action appears. |
| Edit | `user` opens the same journey in edit directly, not a settings dashboard. Header includes 編輯模式 indicator; a compact `.ava-mode-bar` immediately below header and above page control holds 預覽, 儲存修改, 取消修改. Do not replace actual journey back. | Editable elements have a visible pencil and labelled control close to actual content; editing is restricted by App allowlist on render and write. |
| Instructions | On initial User entry show a compact dismissible, non-modal instruction between mode bar and journey page control: **你可以直接喺銷售流程修改可自訂內容，例如標題、說明或指定選項。官方產品資料、保障條款、保費及計算不會改動。** | Dismissal changes no User data and does not move the user to another flow; a new entry shows the instruction. |
| Editable | `.ava-editable` styling plus shared outlined pencil SVG and visible 編輯 label; use labelled input or text area beside/in the actual field. No edit action may trigger customer choice navigation. | Keyboard can activate; labels identify field and page; plain text is escaped on render. |
| Protected | Display as normal readable/selectable content with no edit affordance. Where clarification is needed, add text 官方資料・不可修改 without obscuring content. Do not use a disabled input to imply authorization. | Product values and material qualifications cannot be removed, hidden or overridden by User edits. Existing protected User overrides require separate migration analysis. |
| Preview | Same current page and customer layout using draft; hide editing affordances, show 預覽 indicator, 返回編輯 and 儲存修改. No implicit save. | Return retains draft and page. Preview must show pending values across journey; customer controls remain usable when safe. |
| Success | Show 儲存成功 after write **and readback match**, then return to customer use on the same page where feasible; never report success on a swallowed exception. | Reload restores changes; no Official write. |
| Error | Show 儲存失敗，修改仍保留，請重試 with actionable error, retry and return-to-edit. Do not lose pending changes or last saved snapshot. | Test write failure and readback mismatch independently. |
| Unsaved | Page changes preserve draft. If action would discard it, modal: 尚有未儲存的修改。要放棄修改嗎？; 放棄修改 is destructive, 繼續編輯 is secondary and initial focus. | Cancel confirmed restores the complete last-saved snapshot; cancel declined keeps draft. Browser beforeunload where supported; no promise for OS kill. |
| Unsupported | User URL opens actual flow with plain notice 此 App 暫不支援自訂銷售內容 and 返回 AVA; no editable region, fake toolbar or fake save. Registry `user=false` until genuinely supported. | Test safe URL, no privileged actions; do not invent fields. |

## Layout, tokens and accessibility

Use the canonical CSS (`tokens.css`, `components.css`) semantic values, not an App-specific palette: `--ava-color-background`, `--ava-color-surface`, `--ava-color-text`, `--ava-color-text-secondary`, `--ava-color-control-border`, `--ava-color-focus`, `--ava-color-primary`, `--ava-color-on-primary`, `.ava-status--success` / `--error` / `--warning`. Use `--ava-font-family`, `--ava-type-page`, `--ava-type-body`, `--ava-type-label`, `--ava-type-button`, `--ava-type-support`, `--ava-gap-component`, `--ava-gap-section`, `--ava-card-padding`, and responsive page/safe-area padding. Current canonical default values are component gap 12px, section gap 28px, card padding 20px, body 16px; tokens remain authoritative if changed. Use 20px outlined SVG, 2-unit stroke, rounded caps/joins; decorative icon is hidden from accessibility tree. Use 44px minimum target height and width for icon-only actions; no text scaling restriction. Primary is 儲存修改; secondary 預覽 / 返回編輯 / 取消修改; destructive confirmation uses danger; Return is secondary link, never an Admin shortcut. Labels do not disappear at narrow width.

At <=650px stack/wrap header and toolbar actions and keep Return visible; >650–1000px use flexible horizontal wrapping, preserving readable customer content; >1000px place toolbar actions in a horizontal row. This is viewport-based, including split iPad and folded/unfolded devices. Header can grow; mode bar uses normal flow unless an App proves sticky behavior does not obscure content/focus. Maintain viewport safe areas and keyboard-reachable controls. Avoid global overflow clipping; only legitimate dense product content may scroll in a labelled, keyboard-focusable local region. Test 650/651 and 1000/1001, narrow phone, folded/unfolded, iPad portrait/landscape, desktop and enlarged text.

Use native buttons/links and associated labels; no color-only status. Preview/edit transition keeps logical reading order and moves focus to the mode heading, or triggering control when appropriate. Success uses a reserved polite live region; errors use accessible assertive status and identify the failed field or action. Modal uses `role=dialog`, accessible name, modal semantics, focus containment, Escape (equivalent to continue editing), and restores focus to initiator. Maintain visible 2px focus outline with 2px offset and respect reduced motion. Avoid live announcements per keystroke.

## State and acceptance

A single App-owned working draft spans pages; snapshot is last successful persisted readback. Edit→Preview changes no persistence. Preview→Edit retains draft; successful Save writes validated allowlisted User overrides only, reads back matching values, and leaves the snapshot recoverable. Failure keeps draft and saved snapshot. Confirmed Cancel restores snapshot, including earlier pages and custom-page changes. Return to AVA and reload protect dirty draft where platform supports; PWA/WebView host lifecycle limitations are reported, not invented. Resolve approved User return destination via existing App contract and `avaSurface=user` where supported; never infer privilege from navigation. A close, Back or reload is not Return to AVA.

Acceptance: (1) all three entries plus invalid input fail safely, unauthorized Admin negative test; (2) edit one permitted field on real flow, navigate pages, preview and return without write; (3) save/readback/reload; (4) cancel and navigation guard with dirty multi-page draft; (5) force write and readback failure, retain draft; (6) protected content/logic unchanged and Official write denied; (7) supported and unsupported declaration cases; (8) User return and responsive/keyboard/status; (9) PWA update while dirty and WebView as environment permits. Distinguish simulated, real browser, actual device and deployed evidence. Mockups are references only, not QA. Existing platform design-system reference preview is [`design-system/preview.html`](../design-system/preview.html); it is not an App implementation screenshot. [Conceptual three-state reference](user-edit-reference.svg) illustrates hierarchy only; it is not an App screenshot, a pixel-exact layout, or QA evidence. Full approved instruction copy remains normative above.

## Capability declaration

An App commits a local manifest conforming to [JSON Schema](user-edit-capability.schema.json), with stable app-owned lowercase field IDs; `appId` must match the actual canonical Platform ID when registered. `entries` indicates *actual supported capabilities*, not URL parsing. `frontend` must be true; `admin` is true only where independently authenticated capability exists. `user=true` iff supported presentation editing exists; a safe unsupported direct `?avaEntry=user` is not a supported editing capability. Supported requires at least one field and a nonempty `userStorage`; unsupported requires no fields and null storage. `userStorage` describes existing app-owned User storage, not credentials or runtime endpoints. Duplicate fields and extra properties are rejected. IDs use lowercase alphanumeric segments separated by `.`, `_`, or `-`, max 128 characters. See [supported](user-edit-capability-supported.example.json) and [unsupported](user-edit-capability-unsupported.example.json) examples. A schema check does not certify that fields are safe; App tests must cross-check render/write allowlists, behavior, persisted readback and negative Official writes. No runtime App depends on this file being served by Platform.
